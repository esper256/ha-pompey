# Bundled applications and ownership

Supervisor builds one immutable amd64 image from `pompey/Dockerfile`. `pompey/vendor_bundle.py` runs only during that build: it verifies artifact checksums, extracts safe archive members, exports the digest-pinned Seerr image and checks out the pinned Recyclarr resource commits. Runtime contains neither this installer nor its download tools. `/opt/pompey` is root owned.

`write_engine_configs.py` writes managed settings before s6 starts applications. Engine binaries and controller jobs run as container root for HAOS SMB compatibility. Arr self-updates are disabled; updates arrive through the add-on image. `recyclarr_sync.py` reads bundled local resources without GitHub access and configures real Default, Max and Anime profiles. A durable image-identity record is accepted only when the profiles still exist in both Arr services.

The controller has bounded, serialized configuration, download, request and routing jobs. Health probes continue independently. Startup uses the real cont-init-before-services ordering rather than engine-download barriers. Configuration failure clears current prerequisite markers and remains visible; initialized Seerr connections and source synchronization are required.

## Conservative files and requests

Arr owns ordinary imports, upgrades and library moves. Prowlarr direct grabs retain a separate category. Pompey submits only Arr-accepted manual imports and records intent before commands. Unknown or ambiguous files and commands remain reviewable. One bad receipt must not authorize duplicate submission or deletion. Downloads are not assumed to originate from Seerr.

Request closeout uses complete stable snapshots and observed ownership. Unknown seasons are preserved. Search identity changes and large history disappearances pause cancellation until an administrator explicitly resets the baseline while keeping current monitoring. Files and in-flight transfers are retained.

## Updates and recovery

`tools/build_engine_manifest.py` resolves stable releases and resource commits into a candidate manifest. Candidates are built and exercised with the same real-application test. Discovery never changes a running installation. Integration scenarios cover fresh installation, movie and TV imports, request closeout, restart and network behavior. The weekly dependency workflow runs Mondays at 05:41 UTC and resolves all application and quality-resource pins into one draft Actions-owned bundle PR. Manual dispatch supports urgent updates. Discovery finishes for the entire bundle before publishing changes; failure leaves the existing candidate untouched. One candidate receives full release and previous-release upgrade acceptance, producing one patch release if it passes. An existing bundle is refreshed rather than duplicated; unchanged failed candidates retain their evidence without automatic retry. A bundle that is already satisfied by main is closed. There is no post-release discovery trigger. Unchanged upstream pins produce no build.

To release a feature PR, dispatch Validation on **main** with `release_pr` set to its PR number. Dependency discovery supplies `candidate_pr` instead. The planner resolves the exact current base, head, synthetic merge commit, tree and stable version, and holds the PR as draft. Read-only jobs test that immutable merge candidate once, including full release and previous-release upgrade acceptance. Publication executes trusted-main code with narrowly scoped write permissions. It checks the workflow attempt, unchanged base/head/tree and strict GitHub Actions branch protection; dependency candidates additionally retain the per-component/file/source restrictions within the bundle. It verifies that the stable PR head has exactly the accepted tree before reporting the full-suite result as `CI required` there. GitHub may regenerate a temporary merge SHA when the PR becomes ready, so it is not a durable check target. Publication marks ready with the workflow token, waits briefly for GitHub to recognize the gate and merges through normal protection. Thus no smaller PR suite or second image build is needed after successful release acceptance. The merged tree is compared with the accepted tree before an atomic tag and stable source release are published. Failed, cancelled, stale or mismatched candidates cannot publish; full evidence remains available. Rerun the complete release workflow for a fresh acceptance attempt after failure.

Release approval uses required automated acceptance only. Default tokens remain read-only; only planning and publication jobs receive their necessary write permissions, and no workflow approves reviews. Discovery skips prerelease Pompey versions. Dependabot maintains Docker base-image and GitHub Actions dependencies through conventional PRs; those changes retain ordinary required CI and can use the explicit release path when a product release is needed. It does not publish Pompey container images or modify a running HA installation.

The first live cycle completed on October 27, 2026: [discovery](https://github.com/esper256/ha-pompey/actions/runs/40560580225) found Prowlarr 2.7.0.5723, created [PR #113](https://github.com/esper256/ha-pompey/pull/113), passed [full release and actual 0.5.0 upgrade acceptance](https://github.com/esper256/ha-pompey/actions/runs/40560630829), and published [0.5.1](https://github.com/esper256/ha-pompey/releases/tag/v0.5.1). The Actions bot performed the protected merge; the tag and merge reference the accepted tree. The completion hook accepts GitHub's dynamic `Release PR #…` workflow names as well as `Validation`, restricted to main. Standalone `crane` build-tool maintenance remains tracked in [#110](https://github.com/esper256/ha-pompey/issues/110).

The integration job uses the native Docker/containerd image store and default builder with local layer caching, avoiding a separate BuildKit-container Docker archive export/load. Actions summaries list the actual scenario, startup, shared-check and upgrade timings, including incomplete results when tests fail; build and runner timings remain visible in the job steps.

Home Assistant cold backups provide recovery. Pompey deliberately has no runtime package manager, old binary copies, transaction journal, database rollback, downgrade compatibility or legacy-layout migration. Restoring a backup restores the locally built image and app state through HA; ordinary image updates may migrate upstream databases. This foundation does not prove all historical-database upgrades.

## Dashboard observation definitions

All observations are read-only. The local setup server shares one five-source cache between the overview and detailed diagnostics, refreshing at most every fifteen seconds for routine overview reads and every two seconds for explicit diagnostic reads. Independent application sources are read concurrently; each HTTP read has a two-second socket timeout and a bounded response size. Failed sources retain their last successful value and timestamp with `available: false`. A failed whole source does not fabricate a zero. These are observation timestamps, not a promise that upstream internal state is current.

| Headline | Native source and definition |
| --- | --- |
| Torrents | qBittorrent `/torrents/info`; disjoint downloading, seeding, stalled, paused/stopped, checking/moving and other buckets. `stalledUP` is seeding; `stalledDL` is stalled, not downloading. |
| Monitored | Radarr movie and Sonarr series collections with `monitored: true`; counts titles, not episodes, imported files or requests. |
| Indexers | Enabled Prowlarr sources by unique source ID; available excludes sources whose native `disabledTill` is in the future. Disabled sources are excluded from the denominator. This reflects native backoff, not a fresh live probe of every source. |
| Requests | Seerr `/request/count`; open is pending approval + approved-and-processing + failed. Failed is the remaining native status partition after pending, approved, declined and completed. Available approved requests and completed requests are not open. Partial series availability stays in processing. |

Detailed diagnostics inspect the most recent 100 requests and first 100 native queue records per Arr application, explicitly noting truncation. Seerr→Arr correlation uses movie TMDB or series TVDB identity and exact native title IDs; queue→torrent correlation uses download hashes. Partial TV files do not establish request fulfilment. Library import does not prove media-server discovery or playback. Request/root causes remain unavailable when their required sources fail. Explicit release searches remain bounded and rate-limited per title; opening the dashboard never initiates a release search.

GitHub API reference for automation trust boundaries: [effective branch rules](https://docs.github.com/en/rest/repos/rules#get-rules-for-a-branch). Main has an active ruleset requiring the up-to-date GitHub Actions `CI required` check, with no bypass actors; its existing administrator-enforced classic branch protection remains in place too. Planning and publication read the effective rules using the workflow token's metadata permission. Missing protection or unavailable API evidence refuses promotion before expensive acceptance begins. No Administration-scoped token is stored in Actions.
