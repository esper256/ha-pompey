# Agent development instructions

Read [README.md](README.md), [pompey/DOCS.md](pompey/DOCS.md) and [docs/testing.md](docs/testing.md). Product direction is in [VISION.md](VISION.md).

Supervisor builds `pompey/Dockerfile` locally and starts **one** HAOS add-on container. Installation and operation must not require users to run Docker. Never publish images to Docker Hub/GHCR. A local Docker/Podman build checks the Dockerfile; the scenario checks the actual built musl runtime. Neither reproduces Supervisor. The automated acceptance suite is the release gate; see docs/foundation.md for this campaign. Do not spend the session faking Supervisor.

Run `bash tests/run.sh` for routine work: the default is fast logic and syntax/lint checks, targeting under five seconds total. It never builds Pompey or starts applications. Use local Python, Node.js and ShellCheck, or prepare the small cached development-tool image once with `bash tests/run.sh --prepare`. Do not automatically download/build tools on the fast path. Runtime Python sources use `.py` suffixes; only lint shell entrypoints with shellcheck. Required isolated packet checks belong to PR integration and release acceptance, not the local edit loop.

## PR completion: do not wait for CI

Keep ongoing work in a draft PR; return an existing ready PR to draft before pushing iterative edits. Draft edits run fast checks only. After implementation and relevant fast local validation, push, mark the PR ready and enable auto-merge. Submission runs the core integration journeys and required isolated packet checks; passing required CI permits the merge. A new commit on a ready PR must be tested again. Take at most one non-waiting CI status snapshot after the final push, report passed, failed and pending checks accurately with the PR link, then end the turn. An explicit release hold overrides routine auto-merge when merging would expose a new app version: Home Assistant reads the app configuration from main, not GitHub release tags. Pending CI alone is not unfinished agent work. Do not claim pending checks passed or that the release is validated.

Do not use CI watch commands, repeated polling, sleep loops, background watchers, or scheduled follow-ups to wait for checks. Do not run integration locally for every edit, including simple UI changes. Use fast checks and focused browser inspection as appropriate; let submission CI run the core journeys. Run a focused real-application scenario locally only when diagnosing an observed integration failure or when explicitly requested. Documentation-only changes need diff/format review, not runtime tests.

Fix failures already observed within the task's scope, run the relevant local checks, and push the fix without waiting for the new CI run. Revisit later results when the user requests it. Only wait for CI when the user explicitly asks to wait or a requested merge/release or an end-to-end automation proof requires checking completion. This exception authorizes bounded CI watch commands for that requested operation; ordinary PR completion still ends without waiting. Keep required CI checks intact; never bypass them to merge or release.

The test tiers are `bash tests/run.sh` (fast development), `bash tests/run.sh --pr` (core shared movie, TV episode and executable-exclusion journeys plus required packets), and `bash tests/run.sh --release` (full edge/fault journeys and a configured clone; add `--upgrade-from IMAGE` for a real released-image upgrade). Release acceptance runs on explicit release/candidate dispatch, not every main push. Weekly bundled dependency discovery runs, with manual dispatch for urgent updates; only changed candidates incur release acceptance. Keep one empty fresh-install scenario. Preserve and verify background requests/media, keep complete failure logs, and never retry away a failed scenario. Build amd64 only. `CI required` remains the stable merge gate and stays blocked on drafts until submission. Dependency promotion and automatic release require the full release suite and forward-upgrade coverage.

## Runtime constraints

Torrent clients and synthetic peers may run only inside the dedicated integration harness after it verifies a fresh isolated network namespace with no external interface or route. Local WireGuard fixtures may then be created inside that namespace. Never contact external peers. Use synthetic media, one fixture indexer/tracker and metadata replay. Never change the host firewall or default routes. All shipped applications remain real. Product applications and controller jobs run as container root for HAOS SMB compatibility; preserve existing storage ownership. The synthetic external fixture remains unprivileged. Bootstrap DNS uses the existing nobody identity for endpoint resolution only; never exempt all root DNS traffic from the VPN firewall.

The real service order is s6 cont-init then supervised services. Engines wait for the installed fail-closed firewall and generated configuration; a working VPN is not a startup prerequisite. `wire_stack.py` must fail on a required Prowlarr app/source, downloader category, or initialized Seerr→Arr connection failure. Seerr's public setup wizard is permitted before user id 1 exists; its API key legitimately gets 403 then. After initialization both Radarr and Sonarr are required. Plex/local login and optional Seerr interface settings must not conceal a required miss.

Arr owns normal imports/upgrades; Prowlarr owns native source synchronization. Do not add speculative file deletion, identifier stripping, fake quality profiles, declined-request resurrection or unbounded shell retry loops. Mutating controller jobs share a lock. Supervisor updates the image; HA cold backups provide recovery. Do not restore the runtime engine updater or legacy migration machinery. Release artifacts and resource commits are pinned in the manifest, with candidate discovery separate from promotion.


## Product language

Use neutral, task-focused wording in the UI, configuration help, logs, documentation and CI. Prefer “users,” “application stack,” “integration scenarios” and “age-rating-based routing.” Describe behavior without assuming a family structure, audience or living arrangement. Error messages should identify the problem and provide a relevant next action. Preserve existing configuration keys and storage paths unless a behavioral change is explicitly intended.
